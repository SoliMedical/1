# خريطة Firestore V2 وV3 في Firebase Console

يحفظ المخطط الحالي مساري الاسترداد السابقين `soliMedicalApp` و`clinics`، ويعرض في الوقت نفسه بيانات النظام التشغيلية كـ **مجموعات عليا مستقلة V3**. لا تمثل صفحات التطبيق مجموعات مستقلة؛ فالصفحات واجهة، بينما تفصل المجموعات السجلات التشغيلية المتكررة لتقليل حجم كل قراءة وكتابة وعزل سجلات الأقسام عن بعضها.

المسار التشغيلي الجديد الذي يظهر في جذر Firebase Console هو:

```text
patients | visits | appointments | invoices | prescriptions | expenses | waitingQueue | auditLogs | archiveManifests | settings | catalogs
```

كل وثيقة في هذه المجموعات تحمل `clinicId: "shared-clinic-v1"` الآن. وعند بيع التطبيق لطبيب آخر سيحصل على `clinicId` مستقل؛ لذلك يجب أن تتضمن الاستعلامات هذا الحقل، وتطبقه قواعد Firebase عند تفعيلها. لا يُحذف `soliMedicalApp/sharedClinicData` ولا `clinics/shared-clinic-v1` تلقائياً، ويظلان محفوظين كنسختي استرداد أثناء مرحلة الانتقال.

| القسم الوظيفي | مجموعة V3 العليا | ملاحظة التخزين |
|---|---|---|
| ملفات المرضى | `patients` | وثيقة مستقلة لكل مريض. |
| الزيارات والكشف | `visits` | وثيقة مستقلة لكل زيارة. |
| المواعيد | `appointments` | وثيقة مستقلة لكل موعد. |
| الفواتير | `invoices` | وثيقة مستقلة لكل فاتورة. |
| الروشتات | `prescriptions` | وثيقة مستقلة لكل روشتة. |
| المصروفات | `expenses` | وثيقة مستقلة لكل قيد مصروف. |
| الانتظار | `waitingQueue` | وثيقة مستقلة لكل عنصر انتظار. |
| سجل التدقيق | `auditLogs` | وثيقة مستقلة لكل حدث. |
| الأرشفة | `archiveManifests` | بيانات وصفية قابلة للاستعادة، وليست حذفاً. |
| إعدادات العيادة والطباعة | `settings` | وثائق إعدادات مشتركة خفيفة فقط. |
| القوائم الطبية والقوالب | `catalogs` | قوائم مرجعية وقوالب روشتات متكررة. |

## ربط صفحات النظام بالبيانات الفعلية

لا تحتاج كل شاشة إلى مجموعة خاصة؛ بعض الصفحات تعرض حسابات أو بيانات من أقسام أخرى. إنشاء مجموعة لكل شاشة من هذه الشاشات سيضيف قراءات وكتابات مكررة من دون فائدة. الربط الحالي هو:

| صفحة التطبيق | مصدر بيانات V3 | سبب عدم وجود مجموعة باسم الصفحة |
|---|---|---|
| لوحة التحكم | `patients` و`visits` و`appointments` و`invoices` | مؤشرات محسوبة من السجلات الحالية. |
| إضافة زيارة / كشف | `patients` و`visits` و`prescriptions` | المريض والزيارة والروشتة سجلات مستقلة فعلياً. |
| المتابعة القادمة | `visits` و`appointments` | قائمة مشتقة من تواريخ الزيارة والموعد، لا نسخة مكررة. |
| التقارير | `visits` و`invoices` و`expenses` | تقارير محسوبة عند العرض. |
| الصيدلية والروشتة | `prescriptions` و`catalogs/templates` | الروشتات سجلات منفصلة والقوائم المتكررة قوالب مرجعية. |
| إعدادات الروشتة والطباعة | `settings` و`catalogs` | إعدادات ثابتة وقوائم اختيار، لا سجلات مرضى. |
| المستخدمون والصلاحيات المحلية | محفوظة محلياً وبيانات وصفية قديمة خفيفة | هذا مقصود لحماية مبدأ الدخول المحلي؛ لا تُنقل كلمات المرور إلى Firestore. |
| عضويات Firebase | `members/{uid}` | تُنشأ فقط بعد تفعيل Email/Password وإنشاء هوية المدير الدائمة. |

كما يحتفظ النظام بوثيقة `migrationManifests/{migrationId}` ضمن مسار العيادة للاسترداد وتوثيق عملية النسخ والتحقق، ولا تحمل بيانات طبية تشغيلية.

> **تنبيه:** لا ينبغي إنشاء مجموعات يدوية باسم كل صفحة، ولا نسخ بيانات المرضى إلى أكثر من مجموعة، لأن ذلك يزيد تكلفة القراءة والكتابة ولا يقللها. الإضافة الصحيحة هي فصل كل *سجل تشغيلي متكرر* في وثيقة مستقلة ضمن المجموعة المختصة.

## النتيجة المسجلة

في 21 أغسطس 2026 ظهر في Firebase Console المسار `clinics/shared-clinic-v1` وحالته `migrationState: completed` مع معرّف الترحيل `legacy-v2-2026-08-21-final-001`. وبعد ترحيل V3 واعتماده ظهر في جذر القاعدة فعلياً: `appointments` و`auditLogs` و`catalogs` و`expenses` و`invoices` و`patients` و`prescriptions` و`settings`، إلى جانب مساري الاسترداد `clinics` و`soliMedicalApp`. لا تظهر مجموعة فارغة في Firestore Console، لذا ستظهر `visits` و`waitingQueue` و`archiveManifests` تلقائياً عند وجود وثيقة تشغيلية فيها، من دون إنشاء بيانات وهمية.
