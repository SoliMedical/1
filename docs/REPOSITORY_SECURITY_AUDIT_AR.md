# تدقيق أمان مستودع SoliMedical/1

**تاريخ المراجعة:** 17 أغسطس 2026  
**النطاق:** المستودع العام [SoliMedical/1](https://github.com/SoliMedical/1) والنسخة المنشورة على `https://solimedical.github.io/1/`.

## النتيجة المختصرة

المستودع **عام**، وGitHub Pages منشور من الفرع `main` ومن جذر المستودع. لذلك يستطيع أي زائر رؤية الكود وتنزيله وفحص ملف `index.html` وملف `firebase-config.js`. لا يستطيع الزائر تعديل المستودع مباشرة؛ التعديل يحتاج صلاحية كتابة في GitHub.

المراجعة وجدت أن النسخة العامة تتضمن إعداد Firebase الخاص بالويب، كما تتضمن بيانات دخول ابتدائية ضمن كود العميل. إعداد Firebase للويب ليس كلمة مرور إدارية بحد ذاته، لكنه لا يحمي البيانات إذا كانت قواعد Firestore واسعة، خصوصاً مع استخدام تسجيل دخول Firebase المجهول. بيانات الدخول الابتدائية في كود يصل إلى المتصفح لا تصلح لحماية نظام فعلي أو بيانات مرضى.

## نتيجة فحص جلسة Firebase والوصول غير المصرح به

في ملف النشر `index.html`، يستدعي التطبيق `firebaseAuth.signInAnonymously()` عند تشغيل مزامنة Firebase بعد نجاح تسجيل الدخول المحلي، كما يستخدمه أيضاً لتحميل أحدث قائمة الحسابات من السحابة أثناء تسجيل الدخول المتصل. لذلك **نعم، ينشئ التطبيق جلسة Firebase مجهولة تلقائياً** عند الحاجة إلى المزامنة.

في 17 أغسطس 2026 أُجري طلب قراءة غير مُصادَق عليه لمستند المزامنة الموصفي فقط (`soliMedicalApp/sharedClinicData` مع طلب حقل `_syncMeta` فقط)، من دون عرض أو تنزيل بيانات مرضى. أعاد Firestore نتيجة `HTTP 403 PERMISSION_DENIED`.

> هذه النتيجة تعني أن القراءة من دون هوية Firebase محجوبة حالياً. وهي لا تثبت وحدها أن كل مستخدم مجهول مُصادَق عليه محجوب؛ فذلك يتطلب اختباراً منفصلاً لحالة المستخدم المجهول أو مراجعة قواعد Firestore من Firebase Console.

> أي سر، أو كلمة مرور، أو صلاحية يتم وضعها داخل HTML أو JavaScript الذي يرسله الموقع إلى المتصفح يجب اعتباره مكشوفاً، حتى لو أصبح مستودع GitHub خاصاً.

## ما يمكن للزائر العام فعله وما لا يمكنه فعله

| العنصر | ما الذي يستطيع الزائر العام فعله؟ | مستوى الخطر |
|---|---|---|
| كود التطبيق | قراءته وتنزيله وفحصه | مرتفع لوجود بيانات دخول أو منطق صلاحيات على العميل |
| مستودع GitHub | لا يستطيع التعديل أو الدفع دون صلاحية GitHub | منخفض من ناحية تغيير الكود |
| إعداد Firebase للويب | رؤيته واستخدامه لمحاولة الاتصال بالمشروع | طبيعي لتطبيق ويب؛ الأمان يعتمد على Firebase Rules |
| بيانات Firestore | لا ينبغي أن يقرأها أو يكتبها إلا إذا سمحت القواعد بذلك | مرتفع إذا كانت القواعد تسمح لأي مستخدم مجهول |
| بيانات جهاز العيادة | لا يراها عن بُعد تلقائياً، لكن أي شخص يملك الجهاز أو ملف النسخة الاحتياطية قد يقرأها | مرتفع عند مشاركة الجهاز أو النسخ الاحتياطية |

## الإجراء المقترح

1. **فوراً:** تغيير بيانات مدير النظام الابتدائية في النسخة الحالية، وعدم استخدام كلمة مرور قصيرة أو مشتركة.
2. **قبل إدخال بيانات مرضى حساسة:** مراجعة ونشر قواعد Firestore تمنع القراءة والكتابة العامة، ولا تكتفي بشرط `request.auth != null` إذا كان التطبيق يسمح بتسجيل الدخول المجهول للجميع.
3. **عند بيع النسخ:** استخدام المستودعات الخاصة المنفصلة `soli-clinic-03` إلى `soli-clinic-06` ومشروع Firebase مختلف لكل عيادة، حتى لا تتشارك العيادات قاعدة بيانات واحدة.
4. **للحماية الحقيقية للحسابات:** نقل التحقق من المستخدمين والصلاحيات إلى خدمة خلفية موثوقة أو Firebase Authentication مع قواعد Firestore مبنية على هوية المستخدم/العيادة. لا يمكن جعل نظام كلمات مرور محلي داخل ملف HTML عاماً آمناً بالكامل.
5. **للمستودع:** يبقى `SoliMedical/1` عاماً في الوضع الحالي، وفق قرار المستخدم، حتى يستمر GitHub Pages على الرابط القائم. لا تُنفذ أي خطوة لتغيير خصوصيته ضمن هذا التدقيق.

## قرار النشر

يبقى موقع GitHub Pages عاماً لتشغيل التطبيق، ولا يُغيّر هذا التدقيق خصوصية المستودع أو رابط الموقع. الإجراء الوقائي المتوافق مع ذلك هو عدم وضع كلمات مرور حقيقية أو مفاتيح خدمة داخل ملفات النشر، واستخدام قواعد وصول مدروسة لبيانات Firestore. أما المستودعات الخاصة لكل عيادة فتقلل ظهور الكود ومعلومات الإعداد، لكنها لا تستبدل حماية Firestore أو المصادقة من جهة خادم.
