# بوابة تفعيل قواعد Firebase الحية

**الحالة في 21 أغسطس 2026:** تحققت هوية Firebase الدائمة للمدير وعضويته النشطة بدور `owner` في `shared-clinic-v1`، ثم نُشرت قواعد `firestore.rules` الحية وتأكد تطابق مصدرها المنشور مع الملف المراجع. يبقى الدخول المحلي والعمل دون اتصال كما هما، ولا تعتمد هذه الخطوات على إرسال كلمة المرور إلى Firestore.

> **قيد Storage الحالي:** لا توجد سلة Firebase Storage افتراضية أو إصدار قواعد Storage حي في مشروع `clinic1-ba255` حتى الآن؛ لذلك لم تُنشر `storage.rules`. يلزم إنشاء/تهيئة سلة Firebase Storage أولاً، ثم نشر القواعد والتحقق من رفع الشعار، من دون فتح التخزين للعامة.

> **قاعدة أمان:** لا تنفذ `firebase deploy --only firestore:rules,storage` ما لم تكن هوية مدير دائمة وعضوية `active` موجودتين ومتحققاً منهما. عند نشر القواعد دون ذلك، ستُرفض قراءة وكتابة التطبيق لأن القواعد تشترط العضوية.

| بوابة التحقق | الحالة المطلوبة | كيف تُثبتها | الإجراء عند الفشل |
|---|---|---|---|
| حساب Firebase للمزود Email/Password | مفعّل في Firebase Authentication | من Firebase Console: **Authentication → Sign-in method → Email/Password** | فعّل المزود أولاً؛ لا تغيّر الدخول المحلي داخل التطبيق. |
| كلمة مرور المدير المحلي | ستة أحرف أو أرقام على الأقل | من **الإعدادات → هوية Firebase وعضوية العيادة → الانتقال الآمن لتحديث كلمة المرور** | احفظ كلمة مرور جديدة محلياً، ثم أعد محاولة تهيئة الهوية. لا تُرسل كلمة المرور إلى Firestore. |
| الهوية الدائمة | `firebaseIdentityStatus` يعرض هوية دائمة و`uid` غير فارغ | من داخل التطبيق: **تهيئة هوية Firebase الدائمة** ثم **تحديث الحالة** | أبقِ القواعد غير منشورة؛ يعمل التطبيق محلياً أو بالجلسة الاحتياطية إن توفرت. |
| عضوية المدير | وثيقة `clinics/shared-clinic-v1/members/{uid}` فيها `status: active` و`role: owner` أو `admin` | نفّذ أداة Admin SDK الموثوقة ثم اضغط **تحديث الحالة** داخل التطبيق | لا تحاول منح الدور من المتصفح؛ قواعد المشروع تمنع ذلك عمداً. |
| سلامة المزامنة | مسار V2 متحقق والبيانات القديمة محفوظة | راجع حالة الترحيل المعتمدة ونتائج اختبارات V2 | أوقف النشر عند وجود اختلاف؛ لا تحذف الوثيقة القديمة ولا أي بيانات مرضى. |
| الوصول إلى الشعار | مدير نشط يستطيع رفع شعار صورة صالح | جرّب شعاراً صغيراً بعد تفعيل العضوية، ثم تحقق من بقائه متاحاً | راجع دور العضوية ونوع الملف وحجمه؛ لا تفتح التخزين للعامة. |

## نتيجة التنفيذ المعتمدة

| البند | النتيجة |
|---|---|
| إصدار الواجهة العامة | نُشر الإصدار `v1.7.0` إلى `SoliMedical/1` وظهر على GitHub Pages. |
| هوية المدير | موجودة ودائمة في Firebase Authentication. |
| عضوية العيادة | نشطة في `clinics/shared-clinic-v1/members/{uid}` بدور `owner`. |
| قواعد Firestore | منشورة في الإصدار الحي `cloud.firestore` وتطابق الملف المحلي حرفياً. |
| قواعد Storage | مؤجلة تقنياً إلى أن تُنشأ سلة Storage الرسمية للمشروع؛ لم تُخفف أي حماية بديلة. |

## تنفيذ العضوية الموثوق

بعد إنشاء هوية المدير الدائمة، استخدم اعتماد Admin SDK محفوظاً في بيئة آمنة، وليس في المتصفح أو المستودع. يقرأ الأمر مسار الاعتماد من متغير البيئة ولا يطبع محتواه:

```bash
cd /home/ubuntu/medicenter-pwa
FIREBASE_SERVICE_ACCOUNT_FILE=/مسار/آمن/للملف.json pnpm firebase:sync-members
```

يُفترض أن تنشئ الأداة أو تستعيد العضوية في المسار التالي، مع الاحتفاظ بالدور الإداري المطلوب:

```text
clinics/shared-clinic-v1/members/{firebaseUid}
```

## قائمة تحقق قبل النشر

يُنفذ المدير هذه الفحوص بالترتيب، مع الاحتفاظ بالوثيقة القديمة والنسخة المحلية كما هما:

1. يسجل المدير دخوله المحلي المعتاد؛ لا تغير هذه الخطوة أي آلية دخول.
2. يحدّث كلمة المرور من بطاقة الاستعادة إذا كانت أقل من ستة محارف، ثم يحفظها محلياً.
3. يضغط **تهيئة هوية Firebase الدائمة** ويتحقق أن الحالة لم تعد «احتياطي مؤقت».
4. تُنفذ أداة `firebase:sync-members` باعتماد إداري موثوق، ثم تُفحص العضوية من بطاقة الهوية.
5. يراجع المدير قراءة قائمة المرضى وإضافة زيارة على جهاز متصل وآخر غير متصل. لا يحذف أي سجل أثناء الاختبار.
6. بعد نجاح البنود السابقة فقط، ينشر القواعد:

```bash
cd /home/ubuntu/medicenter-pwa
firebase use clinic1-ba255
firebase deploy --only firestore:rules,storage
```

## تحقق بعد النشر

لا يعتبر النشر ناجحاً لمجرد قبول الأمر. يجب أن يستطيع المدير النشط قراءة البيانات الحالية وإضافة سجل طبي جديد، بينما تبقى الجلسة غير المنتمية أو المجهولة بلا صلاحية. كما يجب التأكد من أن التطبيق ما زال يتيح الحفظ المحلي عند انقطاع الإنترنت، ثم يزامن التغيير عندما تعود الشبكة. قواعد المشروع تمنع حذف المرضى والزيارات والسجلات من المتصفح؛ وهذا مقصود لحماية الاسترداد.

| سلوك مطلوب | ما الذي يحكمه في القواعد |
|---|---|
| قراءة بيانات العيادة | عضوية `active` في العيادة نفسها |
| كتابة المرضى والزيارات والروشتات | أدوار `owner` أو `admin` أو `clinician` أو `assistant` |
| إدارة الإعدادات والكتالوجات | `owner` أو `admin` |
| إنشاء أو تعديل العضوية | مرفوض من المتصفح؛ Admin SDK فقط |
| حذف السجلات الطبية أو الشعارات | مرفوض من المتصفح للحفاظ على الاسترداد |
